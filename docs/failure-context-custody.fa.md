# خطای قبلی، replay و ورودی واقعی core — C4t

PR84 بهنام دو کنترل آفلاین روی API پایدار/SQLite اضافه می‌کند: حفظ خطای
retrieval و ادامهٔ امن، سپس مقایسهٔ تصمیم scripted پس از دو خطای متفاوت.
همان تصمیم بعدی، به‌خودی‌خود ایراد نیست؛ با اطلاعات فعلی یکسان، سؤال لازم هم
می‌تواند یکسان باشد. گزارش او این مرز را درست نگه داشته است.

## چه چیزی مستقل بررسی شد؟

[کنترل capture](../tests/test_failure_context_custody.py) دو تاریخچهٔ کاملاً
ساختگی را از configured app واقعی عبور می‌دهد. app، tracker و اتصال SQLite
بین turnها دوباره ساخته می‌شوند؛ این قسمت restart پردازش یا مرورگر نیست.
فراخوانی adapter factory و ورودی‌های واقعی core، retrieval و reasoner ثبت و
مقایسه می‌شوند.

- خطای اصلی بعد از بازسازی app در DB می‌ماند. replay همان event هیچ allocation،
  retrieval یا reasoning تازه‌ای ندارد؛ Action هم ساخته نمی‌شود.
- پس از پیام تازه، snapshot جاری همان case/revision است. اطلاعات و proposal
  پروندهٔ دیگر وارد آن نمی‌شوند و وضعیت کامل پروندهٔ دیگر ثابت می‌ماند.
- پس از correction، fact فعال نسخهٔ جدید است و query واقعی نسخهٔ کنارگذاشته‌شده
  یا دادهٔ case دیگر را ندارد. شواهدی که ابزار همان نوبت برگردانده، عیناً به
  ورودی reasoner می‌رسد؛ شواهد قدیمی جای آن قرار نمی‌گیرند.
- replay قدیمی بعد از turnهای بعدی هم هیچ کار تازه‌ای نمی‌کند. پاسخ HTTP، view
  جاری را با receipt ورودیِ قدیمی نشان می‌دهد؛ خطای تاریخی جدا در SQL محفوظ است.
  outcome جاری را نباید outcome تاریخیِ همان replay معرفی کنیم.

## مرز مشاهدهٔ outcome

`run_outcome` خطای قبلی در SQLite و نمایش سیستم موجود است، اما در ورودی واقعی
reasoner این دو تاریخچه وجود ندارد. پس شاهدی از تصمیم‌گیری مدل بر اساس آن
outcome نداریم. برابری این ورودی‌ها برای دو fixture، استقلال علّی همهٔ مسیرها
یا رفتار تمام مدل‌ها را ثابت نمی‌کند. این‌ها کنترل نرم‌افزار با ports ساختگی‌اند،
نه نمرهٔ کیفیت مدل.

نتیجهٔ retrieval جاری به reasoning می‌رسد و اصلاح fact کاربر در query به کار
می‌رود؛ این را از مصرف outcome عملیاتیِ turn قبلی جدا گزارش می‌کنیم. صرفِ
اضافه‌کردن متن خطا به prompt یا مجبورکردن دو تصمیم به متفاوت‌بودن، بهبود کیفیت
را نشان نمی‌دهد. برای این تحویل، قرارداد model/context یا recipe عوض نشده است.

اگر بعداً outcome قبلی برای تصمیم لازم شد، باید قبل از ingress تازه خوانده شود؛
بعد از آن، outcome جاری ممکن است متعلق به turn جدیدِ در حال اجرا باشد. projection
آینده به case، revision قبلی و run متفاوت bind شود و فقط status/code و شمارش
مجاز را حمل کند؛ trace، متن خام خطا، fact یا مجوز approval نسازد. چنین تغییری
به ثبت تنظیم تازه و مقایسهٔ جدا نیاز دارد و در این مرحله فعال نشده است.

## شواهد و دستور

PR82 فقط مستندات عملیاتی بهنام را اضافه می‌کند. source/ancestry رسیدها بررسی
شده‌اند؛ مشاهده‌های Windows، proxy خصوصی و زمان دقیق اجرای قدیمی، مستقل در
این مرحله بازتولید نشده‌اند. receiptهای قدیمی دست‌نخورده‌اند و محدودیت‌های
گزارش او باقی‌اند. PR84 و capture مکمل آن در
[رسید این مرحله](receipts/team-closeout-2026-10-17.json) به hash/source مشخص وصل‌اند.

```bash
uv run pytest tests/test_failure_outcome_next_turn.py tests/test_failure_context_custody.py -q
```

این دستور فقط fixtureهای ساختگی و SQLite موقت دارد؛ test ارزیابی را نمی‌خواند.
بستن این برش از پذیرش، T4 یا کیفیت مدل را کامل اعلام نمی‌کند. halt، سه hold و
تمام هویت‌های بستهٔ API حفظ‌اند.
