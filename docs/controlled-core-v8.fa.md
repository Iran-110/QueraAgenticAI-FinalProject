# آزمایش کنترل‌شدهٔ core روی Issue واقعی — ۹ اکتبر ۲۰۲۶

این مرحله دو مرز core را بهتر کرده است: جلوگیری اختیاری از تکیه به سندِ نسخهٔ
دیگر، و تبدیل محدود پاسخ صریح نسخه به اطلاعات منسوب به کاربر. پیشنهاد همچنان
از اجرا جداست؛ هیچ اقدام tracker انجام نشده و پیش‌فرض تولید تغییر نکرده است.
ساختار تک agent و قراردادهای فعلی RAG/tracker/UI حفظ شده‌اند.

## چه چیزی را اندازه گرفتیم؟

ورودی‌ها، منابع، پیشنهادها و معیارها در commit `8814fbb` پیش از اجرای سناریوها
ثبت شدند. شش سناریو از یک خانوادهٔ توسعهٔ مرتبط با
[Issue #12782](https://github.com/streamlit/streamlit/issues/12782) داریم:
شواهد کامل برای مکانیزم محدود، حذف شاهد مهم، نسخهٔ کاربر نامعلوم با منابع
مختلط، اصلاح نسخه، تضاد هم‌نسخهٔ ساختگی و حذف شاهد قبلی در refinement.

«شواهد کامل» به معنی حضور شاهد رسمیِ مکانیزم هویت ویجت است. برنامهٔ کاملِ
خراب‌شده و مسیر callback آن هنوز موجود نیست؛ نمونهٔ کاهش‌یافتهٔ گزارش‌شده
کار می‌کند. صورت مسئلهٔ قابل مشاهده، تمام متن اولیهٔ Issue نیست.

متن اصلی و نظرهای همان Issue برای انتخاب سناریو و مکانیزم بررسی شده‌اند.
حتی در متن اولیه، workaround تغییر state گزارش شده بود؛ آن را عمداً از
ورودی سناریو کنار گذاشتیم. هیچ متن پاسخ، workaround یا نتیجهٔ بسته‌شدن Issue
در bundle اصلی شواهد قرار ندارد، اما انتخاب مسئله از پاسخ مستقل نبوده است.
منابع رسمی ثابت به commit مستندات
`695e6ce2fb1b23afc6df66b40420ab0013ad72fd` متصل‌اند.

پیشنهادهای کامل و برچسب‌های مثبت/منفی را Codex هنگام پیاده‌سازی fixture نوشته
و دستیار مستقل با منابع تطبیق داده است. این‌ها پاسخ تولیدشده از درگاه Metis
یا برچسب طلایی انسانی نیستند. reasoner آزمایش فقط توالی ثابت را بازمی‌گرداند؛
هیچ مدلِ پروژه برای انتخاب تصمیم فراخوانی نشده است. بنابراین نتیجه، رفتار
کنترل‌شدهٔ کد است؛ کیفیت مدل، کیفیت RAG، حل Issue واقعی یا موفقیت test نهایی
را نشان نمی‌دهد.

## baseline و مقایسه

ابتدا وضعیت واقعی Git و دستورالعمل‌ها بررسی شد: شاخهٔ کاری
`feat/agent-core-integration`، کد پایهٔ `dad3202` و working tree پاک بود.
۱۱۴۹ تست پایه پاس شدند. سپس ورودی‌های آزمایش ثبت و دو قابلیت اختیاری اضافه شدند.

برای بررسی نسبت baseline با کد قبلی، ۱۴ توالی ثبت‌شده واقعاً روی کد استخراج‌شده
از Git در `dad3202` اجرا شدند؛ checkout اصلی تغییر نکرد. نتیجهٔ این اجرا با
حالت پیش‌فرض فعلی `all` در status، تصمیم، error، تعداد فراخوانی و شناسهٔ
شواهد ارسالی برابر است. رسید جداگانه و اسکریپت بازتولید در مخزن قرار دارند.

| معیار روی پیشنهادهای ثابت | baseline: `all` | `exact_user_version` |
| --- | ---: | ---: |
| پیشنهاد منفی پذیرفته‌شده | ۶ از ۷ | ۴ از ۷ |
| پیشنهاد مثبت حفظ‌شده | ۷ از ۷ | ۶ از ۷ |
| انطباق با رفتار از پیش ثبت‌شده | ۱۴ از ۱۴ | ۱۴ از ۱۴ |

دو خطای مربوط به اتکا به release نسخهٔ نامعلوم یا نسخهٔ superseded اکنون
با `UnknownEvidenceReference` متوقف می‌شوند. این توقف، پاسخ مفید یا حل مسئله
نیست؛ یک مرز پذیرش بهتر است. عدد ۱۴ از ۱۴ هم «دقت تصمیم» نیست: باقی‌ماندن
خطاهای خارج از دامنه و ردِ مقایسهٔ تاریخی درست نیز پیشاپیش ثبت شده بودند.

هزینهٔ سخت‌گیری روشن است: پیشنهاد مثبتی که فقط تفاوت تاریخی ۱٫۵۰ را توضیح
می‌دهد و کاربرد آن برای نصب ۱٫۴۹٫۱ را صریحاً رد می‌کند، در حالت سخت‌گیرانه
هم رد می‌شود. به همین دلیل این قابلیت را پیش‌فرض نکردیم؛ مقایسهٔ تاریخی
باید از `all` و بازبینی منابع استفاده کند.

موجودی اطلاعات، سؤال‌های قابل پاسخ، تصمیم‌های مجاز و معیار بررسی کل پاسخ
در fixture ذخیره شده‌اند و به reasoner داده نمی‌شوند. بررسی فقط JSON نیست:
`user_draft`، خلاصهٔ نگه‌دارنده، rationale و ادعای هر citation با span منبع
تطبیق داده شده‌اند. برچسب‌ها نشان می‌دهند کدام پیشنهاد حتی با JSON معتبر غلط است.

چهار پیشنهاد منفی هنوز پذیرفته می‌شوند: علت/fix تضمینی بدون شاهد، علت‌سازی
از توضیح پارامتر `default`، تبدیل تاریخچهٔ بی‌scope به نسخهٔ کاربر، و ترجیح
ادعای ساختگی هم‌نسخه. کنترل نسخه پشتیبانی معنایی را اثبات نمی‌کند و corpus
نامرتبط یا metadata غلط را اصلاح نمی‌کند. بررسی انسانی کل پیشنهاد همچنان لازم است.

## ورودی پاسخ نسخه و اصلاح اطلاعات

در ۱۶ probe ورودی، bare turn هیچ‌کدام از دو پاسخ صریح نسخه را به fact تبدیل
نکرد. `prepare_version_reply` هر دو را با provenance کاربر تبدیل کرد و ۱۴ ورودی
منفی را نپذیرفت. هر ۳۲ انتظار دو مسیر منطبق بود. اصلاح نسخهٔ ثبت‌شده هم
revision را یک بار جلو برد، نسخه و استنتاج قبلی را superseded کرد و references،
بررسی‌های بدون scope و پیشنهاد معلق قبلی را کنار گذاشت.

helper فقط کل پیام `1.50.0` یا `Streamlit 1.50.0` را می‌پذیرد. عبارت احتمالی،
نقل‌قول از مستندات، نسخهٔ سرور دیگر، پیام چندخطی و «بررسی را انجام نداده‌ام»
به اطلاعات قطعی یا check انجام‌شده تبدیل نمی‌شوند. متن سؤال و متن نمایش‌داده‌شده
باید با `STREAMLIT_VERSION_QUESTION` دقیقاً یکسان باشند؛ نام فیلد به‌تنهایی کافی
نیست. اصلاحات، تغییر محیط و wording دیگر از `UserTurn` صریح عبور می‌کنند.

این مسیر parser عمومی چت نیست. نتیجهٔ check جدید نیز باید به‌صورت fact/اصلاح
صریح وارد شود؛ ثبت صرفِ `checks_performed` همهٔ استنتاج‌های قبلی را باطل نمی‌کند.
این محدودیت را در اتصال UI/tracker باید رعایت کنیم.

## اتصال تیم و حفظ اختیار اجرا

| بخش | ورودی/خروجی لازم برای اتصال |
| --- | --- |
| RAG حسن | `RetrievalRequest → EvidenceBundle` با snapshot ثابت، span و provenance، نسخه‌های دقیقِ تأییدشده، حفظ منابع لازم در دور بعد داخل `top_k`؛ فهرست quarantined family باید در ساخت corpus اعمال شود |
| tracker و ابزارهای محمد بهنام | state و سؤال معلق معتبر؛ raw event/hash و projection آماده‌شده؛ transaction و CAS روی revision، dedupe پیش از بررسی pending/stale، invalidation تأیید قبلی، approval متصل به متن دقیق پیشنهاد و اجرای idempotent |
| UI و ارزیابی محمدحسن | نمایش سؤال canonical برای مسیر نسخه یا فرم facts صریح؛ نمایش پیشنهاد و محدودیت‌ها؛ خواندن state ذخیره‌شده، ارزیابی کل متن و جداسازی dev/test در سطح خانواده |

همهٔ مدل‌های اشتراکی و portها همان قرارداد قبلی هستند. helper اجازهٔ ذخیره یا
تأیید نمی‌دهد. tracker باید سؤال ذخیره‌شده را احراز کند؛ replay ورودی خام را
پیش از اجرای دوبارهٔ helper تشخیص دهد، چون hash خام و آماده‌شده متفاوت است و
سؤال بعد از اولین commit دیگر معلق نیست. جزئیات در راهنماهای اتصال/نوبت کاربر است.
تأیید، restart و جلوگیری از اجرای تکراری باید در tracker واقعی آزمایش شوند؛
این مرحله پیاده‌سازی ذخیره‌سازی یا ابزارهای هم‌تیمی را تکرار نکرده است.

خانوادهٔ `12782` و duplicate تأییدشدهٔ `12629`، همراه reservationهای قبلی
`8061`، `16914` و ارتباط موقت `8901`، در فایل ثبت‌شده قرنطینه‌اند. این یک ورودی
ماشین‌خوان برای سازندهٔ corpus است؛ اعمال‌شدن آن روی index واقعی هنوز باید
با حسن/ارزیابی بررسی شود. پاسخ‌ها، نتیجه‌ها و duplicateها نباید وارد RAG واقعی شوند.

## هزینه و اجرای دوباره

هزینهٔ تازهٔ API صفر است؛ `.env` و کلید استفاده یا چاپ نشده‌اند. ledger اصلی
بدون تغییر است: سقف ۴٫۵ دلار، برآورد settled برابر `0.120888405` دلار، pending
صفر، uncertainty برابر `0.02` دلار، available برابر `4.359111595` و `halted=true`.
علت uncertainty یک `ProviderModelMismatch` حل‌نشده است. ادامهٔ مجاز قبلی فقط
`0.007784635` دلار دارد. رسید واقعی مصرف/صورتحساب و هویت مدل ارائه‌شده هنوز
تطبیق داده نشده‌اند؛ halt یا hold را برای اجرای آزمایش تازه پاک نکردیم.

```bash
uv sync --locked --group dev
uv run python -m agent_app.reasoning.controlled_experiments --validate-only
uv run python -m agent_app.reasoning.controlled_experiments
uv run python scripts/replay_original_controlled_baseline.py
uv run pytest
uv run ruff check .
uv run ruff format --check .
```

برای رسید جدید، `--output` با مسیر تازه گزارش کامل می‌سازد؛ فایل موجود overwrite
نمی‌شود. هیچ فرمان بالا paid call ندارد. فایل‌های بازبینی:
