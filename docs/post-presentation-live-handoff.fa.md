# تحویل کار live پس از ارائه — Member 4

تاریخ: ۲۲ اکتبر ۲۰۲۶. مالک اجرا و review: **محمدحسن گل‌محمدیان، Member 4**.
درخواست ساسان این است که تحویل نهایی گزارش و ارائه جلو برود؛ بررسی و اصلاح
کوچک قابلیت استفادهٔ live را محمدحسن با agent خودش انجام دهد. این سند برنامهٔ
کار است؛ هیچ اصلاح runtime یا آزمایش تازه‌ای با نوشتن آن انجام نشده است.
وضعیت و checkboxها فقط در [plan اصلی، PD1–PD3 و L1–L4](../plan/plan.md)
نگهداری می‌شوند. نام کامل از اسلاید اول
[ارائهٔ v5](presentation/judges-presentation-fa-v5.html) تطبیق داده شده است.

## هدف و دامنه

خروجی مطلوب یک مسیر اجرای قابل فهم و قابل تکرار با همان سیستم ارائه‌شده است.
محمدحسن ابتدا وضعیت موجود را review می‌کند و در صورت وجود blocker مشخص،
تغییر کوچک لازم را می‌نویسد و بررسی می‌کند. نمونهٔ مجاز: آدرس/پورت و مسیر فایل
در تنظیم محلی، ترتیب startup، timeout سازگار با قرارداد موجود، پیام خطای دقیق
و غیرمحرمانه، یا اتصال یک کنترل موجود UI به همان endpoint موجود. تغییر باید
مشکل بازتولیدشده را حل کند و مسیر معمول و پیش‌فرض‌ها را بی‌دلیل عوض نکند.

تعویض مدل/endpoint، dependency یا framework تازه، بازطراحی معماری، تغییر
prompt/renderer/recipe، tuning کیفیت، بازسازی corpus یا index فریز‌شده، تغییر
gold/rubric و تغییر قرارداد مشترک، task این تحویل نیستند. آزمایش‌های C4x/C4y/C4z
به runtime منتقل نمی‌شوند. ایده‌های مستقل در پیشنهاد جدا با دلیل و اثرشان ثبت
می‌شوند؛ در این مرحله پیاده‌سازی نمی‌شوند. اگر هیچ blocker اجرایی پیدا نشد،
تحویلِ خواندنی با نتیجهٔ «تغییر لازم نیست» و مراحل اجرا کافی است.

## baseline ثبت‌شده و چیزی که باید دوباره بررسی شود

این جدول شرح نسخهٔ پذیرفته‌شدهٔ پیش از ارائه است، نه attestation سرویس فعال
۲۲ اکتبر. آغاز L1 باید HEAD واقعی، branch و تفاوت با این شواهد را ثبت کند.
HEAD مخزن هنگام تنظیم این handoff برابر `aa17a4e` بود.

در بررسی remote روز۲۲اکتبر،
[PR #93](https://github.com/Iran-110/QueraAgenticAI-FinalProject/pull/93) با branch
`feat/user-live-backend` و head `11f39d6` باز است؛ مسیر پیشنهادی `user_backend.py`
و ledger مستقل با سقف۱دلار، هنوز بخشی از baseline روی main نیستند. محمدحسن
ابتدا همین پیشنهاد موجود را review و با کار خودش هماهنگ کند تا backend موازی
دیگری ساخته نشود. متن PR هم اجرای سقف کل۵دلار تیم را تضمین نمی‌کند؛ ledger
جدا شاهد رعایت بودجهٔ مشترک، reconciliation یا مجوز دورزدن halt/hold نیست.
وجود این PR مجوز اجرای هزینه‌دار، پذیرش طراحی یا merge آن از طرف ساسان نیست.

## گردش کار محدود L1 تا L4

1. **دریافت و حفظ کار موجود:** `git status --short`، remote، branch و HEAD را
   ثبت کنید. پس از حفظ تغییرات خودتان، `git fetch origin` انجام دهید و branch
   کاری مستقل را با `origin/main` به‌روز کنید؛ reset یا overwrite هم‌تیمی نداشته
   باشید. main مشترک با تغییر محلیِ plan لحظه‌ای sync نمی‌شود.
2. **بازبینی بدون مدل:** launcher/runbook و وضعیت read-only را بررسی کنید؛
   آدرس‌ها، پورت‌ها، وجود index/manifest، مسیر SQLite و حالت انتخاب‌شده را
   بدون چاپ secret ثبت کنید. فرمان status یا GET-only healthcheck موجود،
   مدل را صدا نمی‌زند؛ آرگومان‌ها از بستهٔ واقعی همان اجرا برداشته شوند.
   healthcheck تاریخی artifactهای v2 را می‌شناسد؛ آن را تأیید v5 گزارش نکنید.
3. **ثبت مسئله:** برای هر blocker، انتظار، رفتار فعلی، مسیر بازتولید، فایل
   مالک، کوچک‌ترین اصلاح و معیار پایان بنویسید. کیفیت پاسخ/انتخاب منبع را با
   اشکال startup یا wiring مخلوط نکنید. diffِ PR93 را با main مقایسه کنید و
   بخش‌های کوچک قابل استفاده، تغییرات خارج از دامنه و ایراد حساب هزینه را
   جدا گزارش کنید؛ ادغام یا اجرای آن در این handoff انجام نمی‌شود.
   اگر مشکل از هزینه، scope بسته، drift
   pin/watch، مدل یا معماری است، blocker مستقل ثبت شود؛ guard دور زده نشود.
4. **اصلاح کوچک:** فقط فایل‌های لازم در branch خود محمدحسن تغییر کنند.
   هر اصلاح به task L2 و همان issue متصل باشد. در صورت نیاز به قرارداد مالک
   دیگر، تصمیم مستقل و review او لازم است؛ تغییر پراکنده یا refactor ضمیمه
   نشود. تنظیم local/secret و مسیرهای دستگاه وارد Git نشوند.
5. **پذیرش آفلاین:** مسیر متأثر را با provider ماک و storage/index disposable
   بررسی و smoke مرورگر بدون API هزینه‌دار اجرا کنید. baseline و نتیجهٔ بعد
   از اصلاح با شواهد قابل مقایسه ثبت شوند؛ شکست و اجرای مجدد هم نگه داشته شوند.
6. **review و تحویل:** agent محمدحسن diff را از نظر مرز کار، regression،
   اطلاعات محرمانه و دستور اجرا review کند. PR شامل فایل‌ها، source commit،
   دستورها، نتیجهٔ واقعی و محدودیت‌ها باشد؛ checkbox فقط با لینک شاهد بسته شود.

این task مجوز model call، `authorize`، scope تازه، refill، unhalt یا تغییر
ledger اصلی نیست. مجوز محدود تاریخی جلسه به تحویل جدید تعمیم پیدا نمی‌کند.
اگر تغییر به فایل‌های watch یا binding مالی برسد، اجرای scope قدیمی با آن
کد معتبر فرض نشود؛ watch/protocol/hash را برای عبور از drift دوباره نسازید.
اصلاح می‌تواند آفلاین review شود، ولی پذیرش هزینه‌دار احتمالی باید پس از
تصمیم صریح مستقل و بررسی نسخه و scope معتبر انجام شود. خطای نامعلوم dispatch
نباید به retry تازه یا ساخت شناسهٔ جایگزین تبدیل شود.

## معیار پذیرش و شواهد لازم

| کنترل | شاهد مورد انتظار |
| --- | --- |
| startup و تنظیم | مراحل بازتولید قبل/بعد، سرویس و پورت درست، خطای قابل فهم برای تنظیم ناقص؛ بدون فراخوانی provider در startup/status. |
| UI/API | مرورگر به backend درست وصل است؛ متن کامل draft/منابع و review قابل دسترسی‌اند؛ نوع scripted/mock/real از provenance معتبر گزارش می‌شود. |
| وضعیت و approval | correction، approval قدیمی، reject/edit در بخش متأثر درست‌اند؛ approval به همان revision و متن مقید می‌ماند. |
| پایداری | retry همان operation یک action نگه می‌دارد؛ restart/reopen، case switching و نبود نشت بین پرونده‌ها در مسیر متأثر بررسی می‌شوند. |
| مرز داده/هزینه | provider ماک، SQLite/index موقت؛ عدم reset/halt bypass، عدم تغییر fixtures/gold/corpus و عدم انتشار secret. |
| بازگشت | روش برگشت از همان commit یا تنظیم محلی با حفظ دادهٔ کاربر و ledger؛ rollback به معنی reset tracker نیست. |

نقطهٔ شروع تست هدفمند، بسته به فایل متأثر، تست‌های موجود
`test_presentation_runtime.py`، `test_presentation_ui_api.py`،
`test_presentation_session.py`، `test_presentation_review.py` و
`test_ui_persistent.py` در [tests](../tests/) است. برای healthcheck/watch یا
factory از تست همان ماژول استفاده شود؛ همهٔ suite فقط به دلیل اصلاح مستندات
دوباره اجرا نشود. در اجرای گستردهٔ توسعه، پنج مصرف‌کنندهٔ محافظت‌شده دقیقاً
طبق بخش Verification در AGENTS.md deselect و این محدودیت در گزارش ذکر شود.
اجرای تست نرم‌افزار، امتیاز کیفیت مدل یا held-out evaluation نیست.

قالب تحویل L4: «task و مسئله؛ branch/commit و PR؛ تغییر دقیق؛ دستور اجرای بدون
secret؛ تست‌های اجراشده و نتیجه؛ screenshot غیرمحرمانه در صورت نیاز؛ هزینه و
model calls واقعی؛ روش بازگشت؛ blocker و موارد خارج از دامنه». API تازه در
این گردش کار باید صفر بماند؛ نتیجهٔ اجراشده را به receipt تاریخی نسبت ندهید.

## تحویل گزارش و ارائه با ساسان

ساسان گزارش فارسی کوتاه و خوش‌خوان RTL را با چهار نام تیم، معماری، مدل و
بازیابی، دستاوردها و سهم کار مستند آماده می‌کند. سهم‌های انجام‌شده از تاریخچه
و شواهد گردآوری می‌شوند؛ تعداد تست‌ها، availability منابع و کیفیت پاسخ هرکدام
با واحد و دامنهٔ درست نوشته شوند. گزارش، پایان ارزیابی E4/E5 یا C5 را القا
نکند. **فایل گزارش پیش از ورود به Git به ساسان نشان داده می‌شود و تنها پس از
تأیید او منتشر می‌شود.**

فایل نهایی ارائه با نسخهٔ واقعاً استفاده‌شده تطبیق داده شود؛ v5 موجود نقطهٔ
شروع است. عمومی‌بودن repo خواندنی بررسی شود؛ تغییر visibility در این task
مجاز نشده است. گزارش و ارائهٔ نهایی با لینک قابل مشاهده تحویل می‌شوند؛
یادداشت‌های خصوصی presenter، کلیدها، token، ledger و receiptهای خصوصی خارج
Git می‌مانند. کار ساسان در این مرحله شامل اجرای اصلاح live نیست.
