## گزارش‌ها و گفت‌وگوهای GitHub

منبع: فقط API خواندنی عمومی مخزن [`streamlit/streamlit`](https://github.com/streamlit/streamlit/issues). تاریخ snapshot: ۶ اکتبر ۲۰۲۶. دریافت با `gh api -X GET` و احراز هویت موجود انجام شد؛ کلید خوانده، چاپ یا ذخیره نشده است. نسخهٔ صریح API در درخواست‌ها: `2022-11-28`.

انتخاب اولیه با ۸ جست‌وجوی محدود انجام شد: چهار دامنهٔ برچسب `feature:st.session_state`، برچسب `area:widgets`، واژهٔ `rerun` و واژهٔ `callback` در عنوان/بدنه، هر کدام از جدیدترین و قدیمی‌ترین طرف. `is:issue` و کنترل فیلد `pull_request` رکوردهای PR را حذف می‌کنند. هر درخواست تا ۱۰۰ رکورد می‌گیرد. از 535 گزارش یکتا در پاسخ‌ها، 240 گزارش با round-robin و ترتیب ثابت SHA-256 انتخاب شده است. فیلتر بر اساس موفق‌بودن راه‌حل یا وضعیت بسته‌شدن انجام نشده است.

## کیفیت، نسخه و نشت اطلاعات

- **High — نشت پاسخ مستقیم:** ۶ فایل Release Note به ۳۷ گزارش از این مجموعه لینک مستقیم دارند. نگاشت دقیق در `docs_issue_links.json` موجود است. پس از انتخاب eval، صرف حذف نظرهای پرونده کافی نیست؛ بند رفع همان مشکل و اسناد/گزارش‌های خانوادهٔ تکراری نیز باید بررسی و از جست‌وجو حذف شوند. فایل release سالانه را نباید یک chunk واحد گرفت.
- **High — بدنهٔ قابل ویرایش:** بعضی بدنه‌های فعلی، از جمله گزارش [#16732](https://github.com/streamlit/streamlit/issues/16732)، بعداً با تشخیص علت یا نتیجهٔ آزمایش ویرایش شده‌اند. API فعلی متن اولیهٔ تاریخی را تضمین نمی‌کند. ورودی شروع eval باید توسط انسان تهیه شود؛ تمام متن فعلی را به نام «گزارش اولیه» به مدل ندهید.
- **High — اختلاف نسخه:** docstringهای این snapshot تا 1.64.0 هستند، اما [#17249](https://github.com/streamlit/streamlit/issues/17249) به 1.65.0 نیز اشاره می‌کند و [#5618](https://github.com/streamlit/streamlit/issues/5618) مثال 1.11.1 دارد. مستندات خارج از نسخه نباید اثبات قطعی برای محیط کاربر تلقی شوند.
- **High — تغییر رفتار callback:** در [Release Notes نسخهٔ 1.63.0](https://github.com/streamlit/docs/blob/695e6ce2fb1b23afc6df66b40420ab0013ad72fd/content/develop/quick-references/release-notes/2026.md)، رفتار `st.rerun()` و `st.switch_page()` داخل callback نسبت به گذشته تغییر می‌کند. ادعای عمومی و بدون شرط نسخه دربارهٔ no-op بودن این فراخوانی‌ها خطاست.
- **Medium — ارتباط موضوعی و نوع پرونده:** در نمونهٔ اولیه 130 گزارش برچسب `type:bug` و 102 گزارش برچسب `type:enhancement` دارند؛ برچسب‌ها ممکن است هم‌پوشانی داشته باشند. همهٔ این 240 مورد ورودی مناسب برای support/eval نیستند. درخواست قابلیت و گزارش ظاهری/استقرارِ نامرتبط باید در بازبینی دامنه حذف یا جدا شود.
- **Medium — وضعیت، پاسخ صحیح نیست:** 161 گزارش بسته و 79 گزارش باز هستند. حتی `completed`، `duplicate` یا نسبت نویسندهٔ `MEMBER/CONTRIBUTOR` به‌تنهایی اثبات رفع مشکل یا صحت پاسخ نیست. هیچ gold label از این فیلدها تولید نشده است.
- **Medium — خانوادهٔ تکراری:** فایل `catalog/family_review_candidates.json` پیوندهای صریح بین گزارش‌های منتخب را برای بررسی ارائه می‌دهد. پیوند عمومی به یک گزارش دیگر به‌خودی‌خود خانوادهٔ تکراری را ثابت نمی‌کند؛ تصمیم با بازبین است.
- **Low/expected — منابع چندرسانه‌ای:** برخی نمونه‌ها به ویدئو، تصویر یا برنامهٔ زنده لینک می‌دهند؛ این فایل‌ها در snapshot متن موجود نیستند. agent باید شواهد متنی موجود را ارجاع دهد و خروجی غایب را حدس نزند.

## تقسیم پیشنهادی قبل از هر index یا embedding

1. مسئول ارزیابی از seed pool حداقل ۳۰ پروندهٔ متنوع را **با بازبینی انسانی** برگزیند؛ ۱۵ dev و ۱۵ final test. در هر دو بخش، موارد قابل پاسخ، نیازمند سؤال و نیازمند ارجاع حضور داشته باشند. این سه نتیجه نباید از `state_reason` یا یک قضاوت خودکار تولید شوند.
2. تقسیم در سطح پرونده و خانوادهٔ تکراری باشد. تمام رکوردهای issue، نظرها، نتیجه‌ها و برچسب‌های نهایی ۳۰ پرونده و اعضای خانواده‌شان، پیش از ساخت RAG در مسیر evaluation-only قرنطینه شوند. پروندهٔ dev هم عضو corpus نیست؛ تفاوت dev/test در اجازهٔ tuning است.
3. برای هر سناریو `visible_input`, `starting_turn`, `allowed_evidence`, `missing_information` و چند نتیجه/قدم بعدی قابل دفاع تعیین شود. نظرهای آینده طبق نوبت آشکار شوند. پاسخ طراحی‌شدهٔ کاربر از گفت‌وگوی واقعی علامت‌گذاری شود.
4. حداقل ۱۰ سناریوی چندنوبتی، شامل حداقل ۵ final test، ساخته شود. اصلاح نسخه/واقعیت، رد/ویرایش پیشنهاد، توقف و ادامه، درخواست تکراری، تغییر پرونده پیش از اجرا، خطای ابزار و جداسازی دو پرونده باید پوشش داده شوند.
5. پیش از freeze، `docs_issue_links.json` و candidateهای خانواده بررسی شوند. بندهای پاسخ‌دهنده به همان پرونده از docs/Release Notes حذف یا قرنطینه شوند. برای benchmark تاریخی، تاریخ هر مدرک باید پیش از زمان سناریو باشد؛ در غیر این صورت benchmark را snapshot/current بنامید و محدودیت نسخه را واضح ثبت کنید.
6. corpus فقط از **allowlist صریح** ساخته شود؛ اگر split/allowlist تثبیت نشده، indexing متوقف بماند. انتخاب فعلی تمام داده‌ها در یک پوشه، مجوز indexing تمام آن‌ها نیست.
7. برای شروع کم‌هزینه، Markdown بر اساس heading و کد به‌صورت rule-based تقسیم شود. docstringهای یکسان با hash deduplicate و فهرست نسخه‌های معتبر حفظ شوند؛ هزینهٔ تعبیهٔ 1,172 رکورد تکراری بی‌دلیل پرداخت نشود. baseline آفلاین BM25/TF-IDF می‌تواند قبل از هر embedding پولی ساخته شود.

## بازسازی و بررسی

دستورها و روش resume در `../data-prep/README.md` موجود است. `fetch_snapshot.py` پاسخ‌های موفق قبلی را با hash کنترل و reuse می‌کند؛ سقف مجموع درخواست‌های ذخیره‌شده 290 است و retry محدود دارد. `inspect_snapshot.py` آفلاین تعداد، شناسه‌های تکراری، comment count، پایان pagination و hash پاسخ‌ها را بررسی می‌کند. manifest تهیه‌شدهٔ نهایی hash فایل‌های snapshot و ابزار آماده‌سازی را دارد.

GitHub یک دیتاست immutable نیست: دریافت تازه در روز دیگر، دادهٔ تاریخی دقیق را بازسازی نمی‌کند. بازتولید **همین** آزمایش با توزیع snapshot ثابت و hashها ممکن است؛ مستندات با commit ثابت دقیقاً بازسازی می‌شوند. کلید یا اعتبار ۵ دلاری برای این آماده‌سازی مصرف نشده است.

منابع اصلی برای معنای endpointها: [GitHub issue comments](https://docs.github.com/en/rest/issues/comments#list-issue-comments)، [جست‌وجوی GitHub](https://docs.github.com/en/rest/search/search#search-issues-and-pull-requests)، [صفحه‌بندی GitHub](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api).
