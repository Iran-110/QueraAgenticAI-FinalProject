# C5: بررسی فقط‌خواندنی سه درخواست نامعلوم

**C5 هنوز باز است؛ بررسی محلی آن کامل‌تر شد، اما مبلغ واقعی این سه درخواست معلوم نشد.**
ledger، holdها، halt و تمام رسیدهای قبلی حفظ شدند. هیچ کلید، فایل credential،
سرویس خارجی یا API خوانده/فراخوانی نشد و هیچ مجوز live تازه‌ای ایجاد نشد.

[بستهٔ ماشین‌خوان](c5-readonly-audit-v1.json) با
[اسکریپت فقط‌خواندنی](c5-readonly-audit-v1.py) ساخته شد: ۳۶ کنترل local custody
پاس‌اند؛ این عدد، تأیید صورتحساب یا نتیجهٔ کیفیت مدل نیست.

## وضعیت واقعی ledger

| مورد | مشاهدهٔ محلی |
| --- | --- |
| reservation | ۷۱۸: ۷۱۵ settled و سه uncertain |
| pending | صفر |
| مجموع تخمین settled با قیمت pinشده | `$0.599798760` |
| مجموع reservationهای uncertain | `$0.030137600` |
| توقف عمومی / سقف runner | `halt=true` / `$4.50` |
| تطبیق حساب provider و مصرف همهٔ اعضا | انجام نشده |

hold مبلغ واقعی مصرف نیست؛ `null` هم به معنی صفر نیست. این اعداد موجودی کیف پول،
صورتحساب نهایی متیس یا هزینهٔ همهٔ لپ‌تاپ‌های تیم را ثابت نمی‌کنند.

## سه پروندهٔ باز

شناسه‌ها در جدول کوتاه شده‌اند؛ شناسهٔ کامل، run/case/revision، timeline، scope
و hash مدرک هر مورد در JSON همراه است. همهٔ زمان‌ها UTC هستند.

| شناسهٔ محلی | مدل درخواستی و بازه | چیزی که واقعاً ثبت شده | چیزی که نمی‌دانیم |
| --- | --- | --- | --- |
| `call:00d470ec…` | `gpt-4.1-mini`؛ ۷ اکتبر، `11:20:50.248` تا `11:20:57.443` | primary receipt اصلی **HTTP 200** و `ProviderModelMismatch` را ثبت کرده؛ reservation اولیه `$0.008560640` بود و با مجوز تاریخی hold به `$0.020000000` افزایش یافت | نام واقعی serving model، usage، شناسهٔ provider و هزینه/refund حفظ نشده‌اند؛ HTTP 200 این‌ها را تأیید نمی‌کند |
| `call:99512367…` | `gpt-4o-mini`؛ ۱۴ اکتبر، `10:01:22.388` تا `10:01:52.399` | `ProviderRequestFailed` و شروع تلاش transport؛ hold برابر `$0.003379200` | HTTP status، دستهٔ دقیق خطا، model، usage و هزینه نامعلوم‌اند؛ حدود ۳۰ ثانیه بودن فاصله، `read_timeout` را ثابت نمی‌کند |
| `call:0377ef42…` | `gpt-4o-mini`؛ ۱۵ اکتبر، `18:05:09.319` تا `18:05:15.805` | observer امن دستهٔ `connect_timeout` را ثبت کرده؛ hold برابر `$0.006758400`؛ ورودی `24045` و زیر حد `32768` بوده | پاسخ HTTP، model/output/usage و هزینه مشاهده نشده‌اند؛ علت جزئی شبکه/DNS/TLS یا صفر بودن هزینه ثابت نشده |

برای مورد اول، نام guard به‌تنهایی نمی‌گوید مدل دیگری حتماً اجرا شده؛ هویت
برگشتی تأیید نشد و مقدار آن نگهداری نشده است. افزایش hold نیز شاهد مصرف نیست.
`schema_valid=false` تاریخی را خطای syntax/ClaimPlan تلقی نمی‌کنیم؛ توقف هویت
مدل قبل از usage قابل استفاده رخ داده است.

برای دو مورد بعد، `http_send_started` پیش از ورود به transport علامت می‌خورد؛
اثبات دریافت درخواست توسط provider نیست. در مورد دوم حتی دستهٔ transport
نگهداری نشده؛ علت را از روی مدت اجرا حدس نمی‌زنیم. در مورد سوم، شکست source یا
schema اثبات نشده است. requestها دوباره اجرا نشدند و ID جایگزین ساخته نشد.

## چه مدرکی کم داریم؟

برای هر بازه، صاحب حساب باید رکورد پاک‌سازی‌شدهٔ dashboard یا پاسخ پشتیبانی
provider را بگیرد که موارد زیر را به **همان درخواست** وصل کند:

1. account/key alias نزد صاحب حساب، زمان UTC، مدل درخواستی و شناسهٔ request/response
   خود provider؛ SHA محلی `call:…` شناسهٔ provider نیست و نباید تطبیق آن فرض شود.
2. وضعیت قطعی دریافت/عدم دریافت، تکمیل/شکست و serving model واقعی.
3. input/output usage، مبلغ و ارز، rate/discount و refund یا مدرک قطعی zero-charge.
4. export مصرف کل حساب در دورهٔ پروژه، شامل embedding، evaluation، مصرف دیگر
   اعضا، اعتبار اولیه و بازپرداخت‌ها. تغییر موجودی کلی به‌تنهایی هزینهٔ یک درخواست
   نامعلوم را مشخص نمی‌کند.

کلید خام لازم نیست و نباید داخل Git، پیام یا screenshot قابل انتشار بیاید.
برای بررسی هزینهٔ قدیمی، هیچ model call تازه‌ای لازم نیست. در این بازبینی
endpoint تازه‌ای کشف یا آزمایش نشد؛ دربارهٔ وجود یا نبود تمام APIهای billing
provider ادعای عمومی نداریم.

## امکانات فعلی کد و محدودیتشان

بررسی زیر **static code review** است؛ هیچ‌کدام فراخوانی نشده‌اند:

- `BudgetLedger.settle` می‌تواند یک reservation موجودِ reserved/uncertain را با
  هزینهٔ USD غیرمنفی و tokenهای واقعی، حتی هنگام halt، ثبت کند. خود این متد مدرک
  provider را نمی‌گیرد و اعتبار آن را بررسی نمی‌کند؛ پیش از هر استفادهٔ بعدی،
  تطبیق مدرک و تصمیم حسابداری باید جداگانه review شوند.
- `release_unsent` فقط برای row در وضعیت reserved و با اثبات no-send است.
  هر سه مورد اکنون uncertain هستند؛ این متد راه حذف آن‌ها نیست و timeout به‌تنهایی
  مجوز آزادکردن hold نیست.
- settlement، مجوز live یا بازکردن کمپین متوقف‌شده نیست. در مسیر عادی، unhalt یا
  refund/reset خودکار نداریم. scopeها و grantهای بسته یا revokeشده دوباره فعال
  نمی‌شوند؛ همهٔ IDهای مطالعهٔ متوقف‌شده همچنان غیرقابل استفاده‌اند.
- مبلغ/ارز/refund باید در مدرک بیرونی روشن باشد؛ با حدس نرخ، ویرایش ردیف settled،
  تغییر opening spend یا ساخت ledger تازه، اختلاف را پنهان نمی‌کنیم.

## شواهد و صحت read-only

- DB اصلی با URI `mode=ro`، `PRAGMA query_only=ON` و transaction خوانده شد؛
  هیچ constructor مربوط به BudgetLedger/gateway یا client شبکه ساخته نشد.
- SHA پیش و پس DB برابر
  `141c3536fb864595d94e0d0dd4a55976418def1012402b70f313c92050222785` بود.
  WAL، SHM و journal در هر دو مشاهده وجود نداشتند. snapshot کامل ردیف‌های هر
  ۱۴ جدول در transaction برابر ماند.
- receiptها و اسناد تاریخی بازنویسی نشدند. سه primary artifact مورد اول با
  hashهای packet خصوصی ۱۱ اکتبر برابرند؛ مسیر مطلق فایل‌های خصوصی صادر نشده و
  alias و hash آن‌ها در JSON کافی است.
- [packet قدیمی C5](../../docs/live-reconciliation-2026-10-11.fa.md)،
  [reconciliation مربوط به C4e](../core_stability_adversarial/stability-cost-reconciliation-v1.json)
  و [بررسی توقف C4j](../core_claim_boundary_v1/provider-stop-review-v1.json)
  هرکدام milestone تاریخی خود را توضیح می‌دهند؛ موجودی فعلی از audit همراه خوانده شود.

قدم بعد حسابداری، گرفتن مدرک provider و تطبیق آن است. تا آن زمان کار آفلاین
می‌تواند ادامه یابد؛ این گزارش اجازهٔ API، پاک‌کردن uncertainty، ادامهٔ شناسه‌های
بسته یا تغییر halt نمی‌دهد. کیفیت مدل، RAG و test نهایی هم با این audit سنجیده نشدند.
