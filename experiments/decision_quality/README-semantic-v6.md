# Offline whole-proposal semantic regression challenges v6

[`semantic-regressions-v6.json`](semantic-regressions-v6.json) contains six paired
scenarios, separate prose-only and isolated-registration negative variants, and
two single controls: **8 synthetic scenarios and 16 complete authored proposals**. All proposals are
`AnalysisResult` payloads, including the user draft, maintainer summary, rationale
and claim/chunk links. No proposal was generated by a paid model call.

Every semantic label and expected detector code is a **synthetic developer
expectation**. This pack is an inspectable offline review aid, not independent
evaluation, human gold, a held-out benchmark, or live before/after performance
proof. The proposals were newly authored after reading the public V5 report and
its documented failure mechanisms. The reused input contexts are already exposed
V4 development fixtures. Related variants must not be counted as independent
observations or used to rank model policies.

## Frozen inputs and source boundaries

Every `case_state`, first `evidence_bundle`, and `proposal_requirements` is an
exact deep copy of the selected public V4 fixture and caller-requirements entry.
`source_case_id` and `source_bundle_index` make each copy inspectable. The pack
records the SHA-256 hashes of both original input files; neither prior fixture
was edited. The first evidence pool is used without simulating a real retrieval
ranking or source discovery.

The six selected source cases are the V4 stale-value, stable-key, deliberate old
snapshot, corrected-version working reduction, exact form-submit signature and
unknown installed-version fixtures. Every source hit retains its original chunk
ID, excerpt, URL, commit, source span and applicability metadata. No new public
or private source was downloaded. The frozen official documentation commit is
`695e6ce2fb1b23afc6df66b40420ab0013ad72fd`.

The concept timing excerpt remains an unversioned October 2026 snapshot with
empty `applicable_versions`. The generated API records are exactly scoped to
1.64.0. Their presence does not establish an older signature or an installed
user version. Known chunk IDs do not establish claim-to-span entailment.

Six scenario messages are exact V4 copies. Two messages append explicitly
marked synthetic questions: hypothetical older-version coverage and a dynamic
`**callback_options` wrapper. The historical question does **not** replace the
active 1.64.0 installed-version fact with 1.27.2. The dynamic mapping is unknown;
no unseen mapping contents or callback target are invented. `context_adaptation`
is null for exact messages and describes each appended hypothetical question.
All origin URLs, issue IDs and creation dates are null; every scenario is
synthetic. User code, proposed code and reported checks were not executed by
this author.

## Paired review dimensions

| Scenario suffix | Positive control | Negative control |
| --- | --- | --- |
| `widget-update-order` | Session State update, then callback, then page rerun; construction-time value capture is a separate mechanism. | Reverses automatic update order and treats an invocation-time state lookup as necessarily old. |
| `stable-key-arity` | Preserves `args=("shade",)` and the required `remember(widget_key)` parameter. | Removes `args` while retaining the required parameter; complete-app, prose-only and isolated-registration variants expose distinct static coverage boundaries. |
| `intentional-old-snapshot` | Preserves deliberate old-value capture and a separate current-state read. | Replaces both comparison entries with current-state reads and erases the requested old value. |
| `working-reduction-facts` | Uses active corrected 1.64.0, preserves the working isolated test, and asks for the absent failing path. | Treats superseded 1.63.0 as current, calls the working reduction a failure, and recommends repeating it. |
| `claim-specific-citation` | Cites callback API for callback-before-rest-of-app and timing excerpt for construction-time args. | Gives substantively suitable advice but attributes capture timing to an API excerpt that does not establish it. |
| `exact-version-coverage` | Applies the exact 1.64.0 signature and declines unsupported hypothetical historical certainty. | Claims the same current signature proves 1.27.2 and every older release have identical callback parameters. |

The stable-key scenario preserves its original **complete-app** negative fence,
including the trailing `st.write(st.session_state.get("remembered"))` call. The
current arity checker conservatively abstains when extra top-level rendering or
other opaque/effectful calls lie outside its proof subset. Its authored semantic
label remains unusable because the required callback argument was removed.

The separate **prose-only** negative makes the same argument-removal
recommendation without a proposed Python fence. Static arity checking abstains
because there is no explicit complete proposed registration to analyze. A fourth
**isolated-registration** negative retains the same import, required handler and
wrong registration but omits the trailing rendering call. Only that narrower
static proof control expects an arity finding; it does not replace the original
application proposal.

This distinction was refined during offline authoring after local static replay
exposed the extra-call coverage boundary. The original full proposal and its
semantic label were preserved rather than altering the code to make an expected
finding pass. This is a documented scope refinement, not a live model result or
before/after semantic improvement.

The additional unknown-version control deliberately fabricates a checked
installed version from current API metadata. Its developer semantic label is
unusable; exact-version static code checks remain inapplicable because the
authoritative input has no active user-supplied Streamlit version. The dynamic
kwargs control is a positive uncertainty example: it declines to certify an
unseen mapping's target or callback arguments.

## Static scope and whole-proposal review

Each variant has two independent annotation groups:

- `expected_check_codes` describes the developer's expected narrow deterministic
  findings. Only `remove-args-isolated-registration` expects
  `callback_arity_mismatch`. The other 15 variants have an empty list, including
  the preserved complete-app and prose-only arity failures and other intentionally
  incorrect proposals.
- `semantic_expectation` supplies the author's full-proposal label and reasons.
  `static_scope_expectation.expected_abstentions` records why narrow checking
  cannot establish the semantic property at issue.

The 16 developer-authored semantic labels are seven acceptable, seven unusable
and two needing revision. Those counts describe the authored controls only.

These labels are not an implemented semantic scorer. No order NLP recognizer,
general entailment engine, new production reasoning/judge agent or default
policy switch is introduced. Static acceptance does not establish correct
prose, preserved user intent, active-fact consistency, useful questions or
supported citations. The required and forbidden term fields used in other probe
suites are intentionally absent here; exact-answer keyword scoring must not be
substituted for source-based review.

An offline runner may replay the fixed proposals through fake ports with checks
off and on, preserving the existing at-most-two-attempt allowance. Such a replay
reports contract acceptance, exposed findings, and bounded recovery separately
from these developer labels. It does not generate fresh proposals or measure a
live model's semantic quality. Code fences may be parsed; never execute them.
Paid execution, source retrieval, keys, ledgers, private raw outputs and formal
held-out data are outside this pack.

## Inspect and validate offline

The repository runner and pack-specific tests are maintained separately from
these two data files. Contract validation of this pack needs only local types:

```bash
PYTHONDONTWRITEBYTECODE=1 uv run --no-sync python - <<'PY'
import hashlib
import json
from pathlib import Path
from agent_app.contracts import (
    AnalysisResult, CaseState, EvidenceBundle, ProposalRequirements,
)

path = Path("experiments/decision_quality/semantic-regressions-v6.json")
pack = json.loads(path.read_text())
frozen = pack["frozen_input"]
for path_key, hash_key in (
    ("path", "sha256"),
    ("requirements_path", "requirements_sha256"),
):
    assert hashlib.sha256(Path(frozen[path_key]).read_bytes()).hexdigest() == frozen[hash_key]
source = json.loads(Path(frozen["path"]).read_text())
source_cases = {case["id"]: case for case in source["cases"]}
requirements = json.loads(Path(frozen["requirements_path"]).read_text())
proposals = 0
for scenario in pack["scenarios"]:
    original = source_cases[scenario["source_case_id"]]
    assert scenario["case_state"] == original["case_state"]
    assert scenario["evidence_bundle"] == original["bundles"][scenario["source_bundle_index"]]
    assert scenario["proposal_requirements"] == requirements[scenario["source_case_id"]]
    CaseState.model_validate(scenario["case_state"])
    bundle = EvidenceBundle.model_validate(scenario["evidence_bundle"])
    ProposalRequirements.model_validate(scenario["proposal_requirements"])
    chunks = {hit.chunk_id for hit in bundle.hits}
    for variant in scenario["variants"]:
        analysis = AnalysisResult.model_validate(variant["proposal"])
        assert all(link.chunk_id in chunks for link in analysis.evidence_links)
        proposals += 1
print(f"validated {len(pack['scenarios'])} scenarios / {proposals} authored proposals")
PY
```

That command verifies data copies, versioned contracts and known citation IDs;
it deliberately does not certify source entailment or semantic labels.
